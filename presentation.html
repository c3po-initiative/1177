“All the things”-proxy…

Journalen FHIR Proxy

A read-only HAPI FHIR R4 server in front of three undocumented
Swedish patient-portal services.

With International Patient Summary (IPS) support via Patient/$summary.

Press → or space to advance · esc for overview

The problem

  • 1177 Journalen is Sweden's national patient portal (Inera AB).
  • No public API. The web client speaks an undocumented ASP.NET MVC dialect that wraps server-rendered HTML fragments inside JSON envelopes.
  • Patient data is split across three sister services, each on a different domain and each behind its own SAML SP:
HostContentProtocol
qa.journalen.inera.seJournal records, diagnoses, meds, …JSON-wrapped HTML
bokadetider.at.1177.seAppointmentsPlain JSON
e-tjanster.at.1177.sePatient inbox / messagesPlain JSON

All three federate against the same Inera IDP at idp.qa.invanar-idp.inera.se, but each demands its own Shibboleth-style login dance.

What we built

A FHIR R4 server that joins all three services behind one Basic-auth credential.

                          ┌─► qa.journalen.inera.se          (HTML in JSON)
GET /fhir/X  ──Basic──►   Proxy  ──► idp.qa.invanar-idp.inera.se   (shared IDP)
                          ├─► bokadetider.at.1177.se/api    (JSON)
                          └─► e-tjanster.at.1177.se/api     (JSON)
17FHIR resource types
3SAML SPs federated
41unit tests

Stack: Java 17+ · HAPI FHIR 8.8.1 · Apache HttpClient 5 · Jsoup · Embedded Jetty

The SAML dance

The same flow, three times, against the same IDP — once per SP.

1. GET   sp/Shibboleth.sso/Login
       ──► 302 chain ─► idp/Citizen?...&id=<authId>             ◄── extract authId

2. POST  idp/no-auth/Citizen/login
         Headers:  id: <authId>       ◄── this header is mandatory
         Body:     {"identifier","password"}
       ──► {"success": true, "redirectUrl": "..."}

3. GET   redirectUrl
       ──► HTML page with auto-submitting <form> carrying SAMLResponse + RelayState

4. POST  sp/(AuthServices/Acs | Shibboleth.sso/SAML2/POST)
         Body:  SAMLResponse=...&RelayState=...
       ──► 302 + Set-Cookie: _shibsession_*=... | JpnApplicationAuth=...

5. GET   sp/  (warmup so cookies bind to the right path)
       ──► 200 — session ready

Implemented three times: InvanarClient, BokadetiderClient, ETjansterClient. Cached per credentials hash for 10 minutes.

The IPS Patient summary

GET /fhir/Patient/me/$summary returns one FHIR Bundle of type document.

┌─ Bundle (type=document, urn:uuid:…)
│
├─ entry[0] = Composition (must be first)
│            ├─ type:     LOINC 60591-5 "Patient summary Document"
│            ├─ subject:  urn:uuid:<patient>
│            └─ section[]   ◄── required + recommended always present
│               ├─ Problems              (LOINC 11450-4)  →  Conditions[]
│               ├─ Medications           (LOINC 10160-0)  →  MedicationStatements[]
│               ├─ Allergies             (LOINC 48765-2)  →  AllergyIntolerances[]
│               ├─ Immunizations         (LOINC 11369-6)  →  Immunizations[]
│               ├─ Results               (LOINC 30954-2)  →  Observations[] + DiagnosticReports[]
│
│                            ◄── optional sections, emitted only when data is present:
│               ├─ Vital Signs           (LOINC 8716-3)   →  Observations[] (growth)
│               ├─ Functional Status     (LOINC 47420-5)  →  Observations[] (survey)
│               ├─ Plan of Care          (LOINC 18776-5)  →  CarePlans[] + ServiceRequests[]
│               ├─ Past History          (LOINC 11348-0)  →  Encounters[] (CareContact)
│               └─ Advance Directives    (LOINC 42348-3)  →  Consents[]
│
├─ entry[1] = Patient                              uv-ips profile tagged
├─ entry[2..n] = every clinical resource           each with Meta.profile = …-uv-ips
└─                                                 fullUrl = urn:uuid:<random>

12 of the 17 mapped resource types feed the IPS bundle (audit/appointments/comms are deliberately excluded — they're not IPS sections). All fetches run in parallel via CompletableFuture over a single cached upstream session. Empty required sections fall back to noKnown entries; empty optional sections use emptyReason: nilknown | unavailable.

Pattern adopted from dhroxy.

Things that bit me · part 1

  • The IDP login needs a per-session correlation id header. The value comes from idp/Citizen?...&id=<authId> after the redirect. Random ids → 412 "Non-matching session ID for new authentications".
  • The login response is not a redirect — it's an HTML page with an auto-submitting SAML form. You must scrape SAMLResponse + RelayState and POST them yourself.
  • Shibboleth SPs HTML-encode RelayState as &#x3a;. Decode to : before form-encoding or the SP returns 500.
  • Apache HttpClient 5's executeOpen ignores setRedirectsEnabled. You have to walk the 302 chain manually.
  • The journalen session needs a warmup GET on / after the SAML POST. Without it, every category call returns {"HasTimedOut": true} despite valid cookies.

Things that bit me · part 2

  • Resource UUIDs are session-scoped. Each fresh login generates new ids for the same underlying records. Search→read across two logins → upstream 500. A 10-min session cache (keyed by hashed creds) solves this.
  • The fs request shape varies per endpoint. Most accept Skip+Take+GetFiltersView; growth, lab-overview and lab-cumulative reject the latter two.
  • HAPI 8.x narrative parser is strict XHTML. Jsoup's clean() emits HTML4 (<br>); HAPI throws "Malformed XHTML: Found </div> expecting </br>". Fix: Jsoup output syntax(xml) + escapeMode(xhtml).
  • HAPI auto-populates Bundle.total from _count if you leave it unset — silently lies about empty result sets. Always set it explicitly.
  • The Behandlingsperiod regex. Splitting "2025-11-11 - -" on \s*-\s* is wrong (matches the date hyphens). Split on the literal " - " instead.

What's still gap

Upstream broken (not our bug)

  • laboratoryoutcome/poll
  • laboratoryoutcome/pollanalysisoverview
  • laboratoryoutcome/pollCumulativeOverview
  • laboratoryoutcome/getallgraphableanalyses
  • growthobservation/poll
  • /search + /search/detailview

All return HTTP 500 regardless of body shape. Likely missing a prerequisite "module init" call. Capturing one HAR with a successful first XHR after login should unblock these — no FHIR-side work needed.

Empty for QA test users

  • CarePlan, Immunization, FunctionalStatus, RelatedPerson, Consent — endpoints work but return zero rows. Need a test account with data to verify the row markup.
  • Patient/me.name — birthDate + gender are derived from the personnummer; the textual name still needs scraping from /Dashboard/GetLegalRepresentation.

Out of scope

  • Writes (POST/PUT/DELETE).
  • BankID / Sambi / real OAuth — only QA's identifier+password test mode.
  • Code-system translation for ICD-10/SNOMED CT — only ATC + NPL on medications.
  • Persistence, distributed caching, multi-tenancy, rate limiting, TLS termination.
  • Production-grade logging hygiene.
